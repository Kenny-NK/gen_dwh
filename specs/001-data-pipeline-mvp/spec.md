# Feature Specification: Data Pipeline MVP (PostgreSQL to PostgreSQL)

**Feature Branch**: `001-data-pipeline-mvp`
**Created**: 2026-03-01
**Status**: Draft
**Input**: MVP для управления потоками данных PostgreSQL -> PostgreSQL через Meltano

## Clarifications

### Session 2026-03-01

- Q: Как идентифицируются арендаторы и как обеспечивается изоляция при доступе к данным? → A: Subdomain (tenant1.app.com) - tenant определяется по subdomain, маппится на Keycloak realm/tenant claim
- Q: Какие поля считаются "чувствительными" и по каким правилам определяется их маскирование? → A: Гибридное - автоматическое определение по паттернам (email, phone, credit card) + явная разметка колонок через Meltano tap metadata
- Q: Какие переходы между статусами разрешены и какие действия их инициируют? → A: Полная модель: draft → paused → running → success/failed; failed → running (retry); success/failed → paused; paused → running

---

## Scope

MVP включает: подключение источников, создание/редактирование потоков, preview, запуск, расписание, статусы, аудит, роли.

**Поддерживаемый сценарий MVP**: только PostgreSQL -> PostgreSQL.

**CDC исключен из MVP**, запланирован в Phase 2.

---

## User Scenarios & Testing

### User Story 1 - Подключение источника (Priority: P1)

Пользователь добавляет источник PostgreSQL, проходит проверку подключения и получает понятный результат.

**Why this priority**: Без валидного подключения невозможно создать поток.

**Independent Test**: Пользователь создает источник с валидными и невалидными параметрами и получает корректный исход (успех/ошибка).

**Acceptance Scenarios**:

1. **Given** пользователь на форме подключения источника, **When** вводит host/port/db/user/password и нажимает Сохранить, **Then** система выполняет тест подключения и сохраняет источник при успехе.
2. **Given** пользователь ввел неверные параметры, **When** нажимает Сохранить, **Then** источник не сохраняется как активный и показывается диагностируемая ошибка.
3. **Given** источник ранее использовался в потоках, **When** пользователь изменяет реквизиты источника, **Then** связанные потоки переводятся в предупреждение/паузу и требуют повторной проверки.

---

### User Story 2 - Настройка потока и preview (Priority: P1)

Пользователь выбирает источник, таблицы и режим загрузки, затем проверяет данные в preview до сохранения потока.

**Why this priority**: Ключевая ценность продукта — управляемое создание корректных загрузок.

**Independent Test**: Пользователь настраивает поток и подтверждает в preview, что данные соответствуют ожиданиям.

**Acceptance Scenarios**:

1. **Given** пользователь выбрал источник, **When** открывает настройки потока, **Then** видит список доступных схем/таблиц источника.
2. **Given** пользователь выбрал режим incremental, **When** выбирает cursor field из списка полей таблицы, **Then** система принимает конфигурацию.
3. **Given** пользователь переходит на preview, **When** запрашивает данные, **Then** показываются первые 100 строк по умолчанию из промежуточного результата.
4. **Given** пользователь включает полный preview, **When** выполняется загрузка preview, **Then** система возвращает не более 10 000 строк с пагинацией/фильтрацией/сортировкой.
5. **Given** в данных обнаружены чувствительные поля, **When** preview открыт пользователем роли User, **Then** чувствительные значения маскируются.

---

### User Story 3 - Target, расписание и первый запуск (Priority: P1)

Пользователь задает target-настройки, расписание, сохраняет поток и получает результат первого запуска.

**Why this priority**: Именно успешная доставка данных в целевую БД завершает основной пользовательский путь.

**Independent Test**: Пользователь сохраняет поток, запускает его и проверяет, что данные появились в target согласно настройкам.

**Acceptance Scenarios**:

1. **Given** пользователь завершил wizard, **When** задает target schema/table, write mode и расписание, **Then** поток сохраняется в статусе draft или paused до запуска.
2. **Given** поток запущен впервые, **When** выполнение завершается успешно, **Then** статус становится success, и пользователь видит уведомление.
3. **Given** во время выполнения возникла ошибка, **When** исчерпаны 5 попыток retry, **Then** поток получает статус failed с текстом ошибки.
4. **Given** выбран write mode upsert, **When** определен ключ из источника или вручную пользователем, **Then** целевая таблица обновляется без дублирования ключей.

---

### User Story 4 - Мониторинг и управление (Priority: P2)

Пользователь на главной странице видит потоки, источники, статусы, историю запусков и может управлять жизненным циклом.

**Why this priority**: Операционная прозрачность нужна для ежедневной эксплуатации.

**Independent Test**: Пользователь видит актуальные статусы, историю и может перейти к проблемному потоку для исправления.

**Acceptance Scenarios**:

1. **Given** у пользователя есть созданные потоки и источники, **When** открыта главная страница, **Then** отображаются списки потоков, статусы и подключенные источники.
2. **Given** поток завершился ошибкой, **When** пользователь открывает карточку/лог, **Then** видит статус, причину ошибки и событие в общем пуле уведомлений.
3. **Given** требуется аудит, **When** пользователь с ролью Admin просматривает журнал, **Then** доступны записи действий за период хранения.

---

### Edge Cases

- Источник недоступен в момент запуска по расписанию.
- Источник изменен (credential rotation/смена host), пока поток активен.
- Таблица источника удалена или изменилась структура колонок.
- Пользователь выбирает incremental field с большим числом NULL.
- Запуск по расписанию совпадает с уже идущим запуском той же таблицы.
- Большой preview-запрос превышает лимит 10 000 строк.
- Неверная timezone или конфликт cron-выражения.
- Потеря прав пользователя в Keycloak во время активной сессии.

## Requirements

### Functional Requirements

- **FR-001**: Система должна поддерживать роли пользователей Admin и User.
- **FR-002**: Система должна поддерживать multi-tenant модель с изоляцией арендаторов через отдельную схему на tenant. Tenant идентифицируется по subdomain (например, tenant1.app.com) и маппится на Keycloak realm/tenant claim.
- **FR-003**: Система должна позволять создавать подключение источника PostgreSQL с параметрами host, port, db, user, password.
- **FR-004**: Система должна проверять подключение при сохранении источника и возвращать явный результат.
- **FR-005**: Система должна позволять редактировать сохраненное подключение источника.
- **FR-006**: При изменении источника система должна останавливать связанные потоки и помечать их как требующие повторной проверки.
- **FR-007**: Система должна позволять создавать поток на базе выбранного сохраненного источника.
- **FR-008**: Система должна показывать список доступных схем и таблиц источника для выбора.
- **FR-009**: Система должна поддерживать режимы загрузки full refresh и incremental по выбору пользователя.
- **FR-010**: Для incremental режима система должна позволять выбрать cursor field из полей таблицы.
- **FR-011**: Система должна предоставлять preview данных из промежуточного результата выполнения.
- **FR-012**: Preview по умолчанию должен показывать 100 строк.
- **FR-013**: Система должна поддерживать расширенный preview до максимума 10 000 строк.
- **FR-014**: Для preview должны поддерживаться фильтрация, сортировка и пагинация.
- **FR-015**: Система должна маскировать чувствительные поля в preview для роли User; Admin может видеть полные значения. Чувствительные поля определяются: (1) автоматически по паттернам PII - email, phone, credit card, passport; (2) явно через metadata в Meltano tap конфигурации.
- **FR-016**: Система должна позволять задать target schema и target table для загрузки.
- **FR-017**: Система должна поддерживать write modes: append, upsert, replace.
- **FR-018**: Для upsert система должна поддерживать выбор ключа из источника либо ручной выбор пользователем.
- **FR-019**: При конфликте схемы target система должна завершать запуск ошибкой с описанием расхождений и требовать ручного подтверждения изменений.
- **FR-020**: Система должна поддерживать сохранение потока как черновика (draft).
- **FR-021**: Система должна поддерживать расписания cron, interval, и manual.
- **FR-022**: Система должна позволять пользователю выбирать timezone для расписания, по умолчанию Europe/Moscow.
- **FR-023**: Система должна позволять настраивать максимальную частоту запусков пользователем.
- **FR-024**: Для одной таблицы одновременно допускается только один активный запуск; другие таблицы могут выполняться параллельно.
- **FR-025**: Система должна поддерживать retry-политику до 5 попыток, после чего поток получает failed.
- **FR-026**: Система должна вести статусы потоков: draft, running, success, failed, paused. Разрешенные переходы: draft → paused → running → success/failed; failed → running (retry); success/failed → paused; paused → running.
- **FR-027**: Система должна отображать ошибки в контексте потока/запуска и в общем пуле уведомлений.
- **FR-028**: Система должна показывать на главной странице список потоков, их статусы, список источников и действия Создать поток/Подключить источник.
- **FR-029**: Система должна хранить историю запусков и аудит действий минимум 100 дней.
- **FR-030**: Система должна поддерживать аутентификацию через Keycloak (OIDC) и назначение ролей из claims токена.
- **FR-031**: Поддержка CDC не должна входить в MVP и не должна блокировать текущие сценарии batch/инкрементальной загрузки.
- **FR-032**: Решение должно быть развертываемым в self-hosted режиме через Docker.

### Key Entities

- **Tenant**: Арендатор системы; имеет собственную область изоляции данных (отдельная схема в БД). Идентифицируется по subdomain и маппится на Keycloak tenant claim.
- **User**: Учетная запись с ролью (Admin/User) и правами на операции.
- **Source Connection**: Сохраненные параметры подключения к source PostgreSQL и результат валидации.
- **Data Flow**: Описание потока загрузки от source к target с текущим состоянием.
- **Stream Configuration**: Настройки выбранной схемы/таблицы, режима загрузки и cursor field.
- **Preview Session**: Параметры запроса preview и его результат (с ограничениями и маскированием).
- **Target Configuration**: Схема/таблица назначения и write mode.
- **Schedule**: Настройки запуска (тип, выражение/интервал, timezone, ограничения).
- **Run Record**: Факт выполнения потока с метаданными, статусом, ошибками и retry-счетчиком.
- **Notification**: Пользовательское сообщение об успехе/ошибке/предупреждении.
- **Audit Event**: Событие изменения сущностей или действий пользователя, подлежащее хранению 100 дней.

## Assumptions & Dependencies

- MVP ограничен объемами клиента среднего уровня (ориентир: до 20 GB по источнику в рамках бизнес-сценария).
- Управление секретами на старте допускается через .env с последующим переходом на более безопасное хранилище.
- Ограничения по количеству одновременных потоков на пользователя в MVP не вводятся.
- Внешние уведомления (email/Slack/webhook) не входят в MVP.
- Авто-эволюция схемы (автоматическое применение schema drift) не входит в MVP.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Не менее 95% корректно настроенных source-подключений проходят тест соединения с первого раза.
- **SC-002**: Пользователь может создать новый поток (от выбора source до сохранения расписания) не более чем за 10 минут в 90% случаев.
- **SC-003**: Первый успешный запуск потока завершается в пределах 1 часа для заявленного объема и показывает success.
- **SC-004**: В 100% неуспешных запусков пользователю доступна диагностируемая причина ошибки в UI.
- **SC-005**: В 100% случаев preview соблюдает лимит до 10 000 строк и применяет маскирование по политике ролей.
- **SC-006**: В 100% потоков соблюдается правило отсутствия параллельных запусков для одной и той же таблицы.
- **SC-007**: История запусков и audit events доступна за последние 100 дней без потери записей.
- **SC-008**: Не менее 90% пользователей целевых ролей (Data Engineer, Аналитик, Администратор БД) успешно завершают основной сценарий без обращения к поддержке.
